SECTION 2 - BUGS (P0 unless stated)
--------------------------------------------------------------------------------

B01 Compile error - features/sales/presentation/widgets/cart_panel.dart
    TextButton.icon(onClearCart: onClearCart, ...) - no such parameter.
    cart_panel.dart, product_catalog.dart and pos_foundation_screen.dart are not
    used by the live code. Delete all three (keep the "quick add" idea from
    product_catalog, see SECTION 5).

B02 Runtime error - Expanded inside AlertDialog.actions
    payment_dialog, return_cylinder_dialog, inventory ItemDetailDialog,
    suppliers, people, sales_history dialogs all put Expanded(child: AppButton)
    in actions. Actions are laid out by an OverflowBar, not a Flex, so this
    throws a ParentData error. Also AppButton uses Size.fromHeight(48), which
    forces infinite minimum width, which breaks in unbounded parents.
    Fix: AppButton minimumSize = Size(0, touchTarget) plus an optional
    `expand: true` flag; dialog actions are plain buttons, no Expanded.

B03 branch_management_screen.dart (three bugs)
    a) `final List<Branch> _branches = const [...]` is immutable. add, delete,
       toggle and edit all throw UnsupportedError. Use a normal list for now,
       then a provider.
    b) `Text('Are you sure you want to delete ""??')` and `Text(' • ')` have
       lost their interpolation. Should show the branch name, and
       '${branch.address} • ${branch.phone}'.
    c) `selectedIndex: -1` fails the NavigationBar/NavigationRail assertion
       when the screen opens. Make selectedIndex nullable in the shell.
    Also: dialog controllers never disposed, no validation (empty names save),
    and delete should become "deactivate" when the branch has sales/stock.

B04 sales_header.dart - receipt field loses focus on every keystroke
    _ReceiptField uses key: ValueKey(receiptNumber). The key changes with each
    character, so the field is rebuilt from scratch after each keystroke.
    Fix: a StatefulWidget with its own controller, synced in didUpdateWidget
    when the parent clears it (or key on a per-sale "resetCount").

B05 sales_header.dart - _DateField creates a TextEditingController inside
    build() on every rebuild (leak, and rebuilt on every receipt keystroke).
    Use InputDecorator + InkWell showing the formatted date. Same mistake in
    reports_screen (TextEditingController(text: 'Last 7 days') in build).

B06 sales_header.dart - customer suggestions crash on arrow keys
    (_selectedIndex + 1).clamp(0, _filteredCustomers.length - 1) throws
    ArgumentError when there are no matches (clamp(0, -1)). Also the list shows
    at most 3 rows (itemCount.clamp(0, 3)) but the selected index can go beyond
    row 3. Fix both; close suggestions on focus loss and Escape.

B07 sales_screen.dart - wrong location on customer change
    onCustomerChanged sets Location.defaultLocation even when the customer's
    own locations do not contain it. DropdownButton then asserts ("exactly one
    item with value"). Use the customer's default location.

B08 sales_cart_controller.dart - undo can duplicate lines
    Remove X, add X again, press Undo: two lines with the same product id ->
    duplicate Dismissible keys -> crash, and stock is not re-checked.
    Fix: undo goes through add() (merge + stock clamp); clear() and any add of
    the same product invalidate the pending undo; support undo of a whole
    clear if you want. qtyInCart should use indexWhere, not a dummy Product.
    Remove the unused remove(int) (removeWithUndo replaces it). Add tests.

B09 inline_cart_tile.dart - quantity edits silently ignored
    _hasCommitted is reset only when the item quantity changes. If the user
    commits the same value, or the controller clamps to stock (typed 100,
    stock 5, quantity stays 5), the flag stays true and every later edit is
    skipped on blur. The text field can also keep showing "100" while the
    real quantity is 5.
    Fix: reset on focus gain; commit only if text differs from the current
    quantity; after commit always resync controller text from widget.item.
    Also give each tile key: ValueKey(item.product.id) in the SliverList so
    controllers/focus do not shift between rows when a row is removed.

B10 sales_screen.dart _save() ordering and safety
    - `_isSaving` is set only AFTER awaiting isReceiptNumberUsed, so a double
      F2 starts two flows. Set it first (try/finally to reset).
    - setState is called in the early-return branch before checking mounted.
    - _showMessage / setState after awaits without mounted checks (also in
      _loadData).
    - _getStock uses firstWhere without orElse -> StateError during reload or
      branch switch.
    - If _loadData() fails after the sale was saved, the catch shows "Error
      saving sale" and the cart is not cleared, so the cashier may retry.
      Saving must be one atomic repository call (see SECTION 3.5).
    - Do not show raw exceptions ('$e') to cashiers; log them, show a friendly
      message.

B11 Cylinder return accounting is wrong
    sales_screen checks ret.cylinderType.toLowerCase().contains('empty') but
    cylinderType is '13kg' / '6kg', so returnedEmptyCylinders is always 0 and

    both Afrigas and Progas lines (brand lost) and asks for a return even on

B12 payment_dialog.dart - business logic errors

    - "Complete" is enabled when payments is non-empty even if a balance

    - SizedBox(width: 500) overflows phones; use ConstrainedBox(maxWidth).

    Suggested primary destinations: Sales, History, Inventory, Customers,
    Reports, and "More" (Suppliers, Staff, Branches, Settings). Max 5 in the

    - Login: validation, error state, Enter submits (AppTextField needs

3.4 Domain models: ONE of each, in the owning feature's domain/ folder
      Branch (id, name, address, phone, isActive)       -> branches/domain
      Customer (id, name, phones[], locations[], balance, creditLimit?)
                                                        -> customers/domain
      Product (id, name, kind, brand?, sizeKg?, price)  -> inventory/domain
      StockLevel (branchId, productId, quantity)        -> inventory/domain
      Sale, SaleLine, Payment, SaleStatus               -> sales/domain

3.5 Atomic sale completion
    Replace saveSale + deductStock loop + _loadData with one repository
    operation, e.g. SaleRepository.completeSale(Sale sale) that, in one
    transaction: re-validates stock, stores the sale, deducts full stock, adds
    returned empties, updates customer balance for credit sales, and checks
    receipt uniqueness (per branch). Idempotent via a client-generated UUID id
    (not millisecondsSinceEpoch) so a retry cannot double-post.

3.6 Target folder tree

        reports/
        people/
        suppliers/

3.7 One formatter set (core/formatters)

3.8 Errors and logging

SECTION 4 - DOMAIN GAPS (LPG-specific, P1)
--------------------------------------------------------------------------------

4.1 Cylinder accounting (your core domain)
    - Product.kind enum: refill, emptyCylinder (outright purchase), accessory.
      Add brand and sizeKg fields. Stop parsing names or cylinderType strings.
    - Return dialog applies only to REFILL lines. Skip the dialog entirely when
      the cart has no refills (today it opens and says "No cylinders in this
      sale").
    - Return rows must carry brand + size (+ which brand was returned if it can
      differ from the one sold; that is common in LPG exchange).
    - Maintain a cylinder ledger per branch / brand / size with FULL and EMPTY
      counts. A refill sale: full -n, empty +returned. Outright empty-cylinder
      sale: empty stock -n, no return.
    - Track "empties owed" per customer when full cylinders leave without an
      empty coming back; show it in the sales header and customer detail.
    - Business decision needed: what happens on no return (deposit / extra
      charge), and on a different-brand return (exchange fee).

4.2 Sale model needs: status (completed / credit / voided / refunded),
    payments list (method, amount, reference), dueDate, cashierId / salesperson,
    branch, createdAt, notes, returned cylinder lines (brand/size/count). Today
    Sale holds one paymentMethod and loses invoices, splits and M-Pesa codes.

4.3 Payments
    - Require an M-Pesa reference when method is M-Pesa; validate format.
    - Complete only when remaining <= 0, OR (registered customer + credit
      allowed + within credit limit) -> saved as credit with due date.
    - Show change due for cash overpayment. Disallow overpay for non-cash.
    - Customer statement + "receive payment against balance" flow.

4.4 Void / refund with permission and mandatory reason, written to an audit
    log (who, when, what). No hard deletes of sales, customers with history or
    branches with stock.

4.5 Receipts: printable/shareable receipt after sale and from History.
    Decide the target: Bluetooth thermal printer (ESC/POS), PDF share
    (WhatsApp), or both. "Print Receipt" in History is currently a no-op.

4.6 Daily close / till reconciliation per branch: cash expected vs counted,
    M-Pesa total, credit issued, empties received vs expected, stock variance.
    This is probably the most valuable report for owners.

4.7 Inventory operations (promised in CLAUDE.md, not built): receive stock from
    supplier, transfer between branches, adjustments with reason, low-stock
    thresholds per product/branch, supplier orders.

4.8 Pricing rules: per-customer prices (restaurants vs households), discount
    or price override with permission, price history. Sale lines keep the
    price at time of sale (already true; keep it).

4.9 Date rules: the sale date picker allows 2000-2100. Limit to today, allow
    backdating only for authorized roles.

4.10 If your five-stage workflow includes dispatch/delivery, the rider role
    needs its own flow: assigned deliveries, collect payment, return empties.
    Confirm the stages before building so Sales does not conflict with them.

4.11 Branch changes during a sale: switching branch must reload products/stock
    and either clear the cart or warn (prices and stock differ). Today the
    switch changes only a string.
